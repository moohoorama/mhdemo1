# 클레임 리플레이 (Claim Replay)

> 턴제 SRPG의 AI 페이즈를 **규칙은 완전한 턴제로 계산**하고, **화면에서는 동시에 움직이는 것처럼** 재생하는 렌더링 기법.
> 한국어로는 "점유 순서 재생". 각 행동이 칸과 유닛을 점유 신청(claim)하고, 겹치는 점유만 순서를 지키며 나머지는 겹쳐 재생(replay)한다.

## 1. 왜 필요한가

턴제 SRPG에서 적 페이즈는 유닛이 한 명씩 움직인다. 병력이 늘면 플레이어는 같은 연출을 수십 번 기다린다.
그렇다고 실제로 동시에 행동하게 만들면 규칙이 바뀐다. 이동 칸이 겹치고, 같은 적을 두고 판정이 엉키고, 결과가 실행 순서에 따라 흔들린다.

클레임 리플레이는 둘을 분리한다.

- **게임 규칙**: 기존과 똑같이 한 명씩, 순서대로 판정한다. 결과는 순수 턴제와 1:1로 같다.
- **화면 연출**: 확정된 결과를 다시 재생하되, 서로 상관없는 행동은 겹치고 상관있는 행동만 순서를 지킨다.

플레이어 페이즈에는 쓰지 않는다. 플레이어의 행동은 하나씩 즉시 재생된다(행동 하나짜리 클레임 리플레이와 같다).

## 2. 용어

| 용어 | 뜻 |
|---|---|
| 페이즈 해결 (resolve) | 페이즈 시작 시, 모든 유닛의 행동과 결과를 화면 없이 순서대로 계산하는 단계 |
| 행동 기록 (action record) | 한 유닛이 한 일과 결과: 경로, 행동 종류, 대상, 피해·사망·버프·밀려남 등 |
| 클레임 (claim) | 행동이 건드리는 대상을 나타내는 키. 칸 좌표 또는 유닛 id |
| 점유 장부 (claim table) | `클레임 → 그 클레임을 마지막으로 등록한 행동` 맵 |
| 선행 (precedence) | 행동 B가 화면에 나오기 전에 끝나야 하는 행동들 |
| 완료 (done) | 행동의 연출과 그 결과 연출(대상의 피격 흔들림, 사망 깜빡임 등)이 모두 끝난 시점 |

## 3. 원리

순서대로 계산한 결과를 겹쳐서 보여 줘도 결과가 같으려면, **같은 것을 건드린 행동끼리만 원래 순서를 지키면 된다.**
이것은 데이터베이스의 *충돌 직렬성(conflict serializability)*과 *선행 그래프(precedence graph)*,
CPU의 *스코어보드(scoreboarding)·비순차 실행*과 같은 원리다. 점유 장부는 스코어보드나 잠금 표 역할을 한다.

## 4. 알고리즘

### 4.1 페이즈 해결과 점유 등록 (화면 표시 없음)

```
claims = {}                        # 클레임 -> 마지막으로 등록한 행동
records = []
for unit in AI 행동 순서:
    action = unit.decide_and_resolve(state)        # 기존 턴제 규칙 그대로, state를 갱신
    keys = claims_of(action)
    action.precedence = { claims[k] for k in keys if k in claims }
    for k in keys:
        claims[k] = action                         # 마지막 등록자로 덮어쓴다
    records.append(action)
```

`claims_of(action)`에 넣는 클레임:

- 행동한 유닛 자신 (유닛 id)
- 이동 전 칸, **이동 경로의 중간 칸**, 이동 후 칸
- 행동 대상 유닛(적·아군 모두: 공격, 버프, 치유 등)과 그 유닛의 칸
- 결과로 영향받은 모든 것: 범위 공격·오라의 칸과 유닛, 밀려난 유닛의 이동 칸, 사망으로 비워진 칸, 반격·지원 공격 같은 반응 행동이 건드린 것

### 4.2 재생

```
waiting = records 전체
playing = {}
매 프레임:
    for action in waiting:
        if action.precedence 가 모두 완료:
            action 재생 시작 (이동 → 행동 → 결과 연출)
    완료된 행동은 done 표시
```

선행이 없는 행동은 페이즈 시작과 함께 바로 움직이고, 선행이 있는 행동은 선행이 **모두** 완료되는 순간 움직인다.

## 5. 규칙과 근거

1. **마지막 등록자 하나만 기억한다.** A → B → C가 같은 클레임을 쓰면 C는 B만 기다려도 된다. B가 이미 A를 기다리므로 순서가 이어진다. 선행 간선 수가 최소가 된다.
2. **경로의 중간 칸도 클레임이다.** 출발·도착 칸만 넣으면 경로가 교차하는 두 유닛이 동시에 지나가며 겹쳐 보인다.
3. **자기 자신도 클레임이다.** 앞에서 맞은 유닛이 나중에 행동하면, 피격 연출이 끝난 뒤에 움직여야 한다.
4. **선행은 여럿일 수 있다(join).** 모두 완료되어야 시작한다.
5. **교착은 생기지 않는다.** 선행 관계는 항상 먼저 해결된 행동에서 뒤의 행동으로만 생기므로 그래프에 순환이 없다.
6. **완료에는 결과 연출이 포함된다.** 대상의 흔들림·사망 깜빡임이 끝나야 그 칸으로 다음 유닛이 들어간다.
7. **결과는 바뀌지 않는다.** 판정과 난수는 해결 단계에서 끝난다. 재생은 이미 정해진 결과를 보여 줄 뿐이다.

## 6. 선택 확장

- **읽기와 쓰기 구분**: 상태를 바꾸지 않고 참조만 하는 클레임(예: 같은 아군의 오라를 받기만 함)은 서로 기다리지 않는다.
  장부 값을 `마지막 쓰기 + 그 뒤의 읽기 목록`으로 바꾸면 된다. 기본은 모든 클레임을 쓰기로 취급한다.
- **구간 단위 클레임**: 행동을 이동과 공격 구간으로 나누어 각각 등록하면, 같은 적을 노리는 두 유닛이 이동은 함께 하고 공격만 차례로 할 수 있다.
- **보기 좋게 다듬기**: 선행이 없는 행동도 0.1–0.25초씩 시차를 둔다. 동시 공격 수에 상한을 두거나 카메라 초점 순서를 정한다.
- **건너뛰기**: 결과가 이미 확정되어 있으므로 재생 중 건너뛰면 최종 상태로 바로 넘어가면 된다. 리플레이와 저장도 기록을 그대로 쓴다.

## 7. 한계

- AI가 결정할 때 **간접적으로** 참고한 것(예: "A가 근처에 있어서 B가 다른 목표를 골랐다")은 클레임에 잡히지 않는다.
  결과의 일관성에는 문제가 없지만, 화면에서 B가 A보다 먼저 움직여 인과가 덜 직관적으로 보일 수 있다.
  중요하면 결정에 쓴 유닛을 "읽기 클레임"으로 등록한다.
- 동시에 너무 많이 움직이면 읽기 어려워진다. 6절의 시차·상한으로 조절한다.

    클레임은 행동 유닛, 출발·경로·도착 칸, 대상 유닛과 그 칸(사망 시 비워지는 칸 포함).

    `Battle.perform`은 피격 흔들림·사망 깜빡임까지 기다린 뒤 끝난다.
  - 유닛 상태는 규칙(`cell`, `hp`)과 화면(`at`, `pos`, `shown_hp`)으로 나뉜다.
  - 6절 확장은 적용하지 않았다(시차·읽기/쓰기 구분·구간 단위 클레임·건너뛰기 없음).
