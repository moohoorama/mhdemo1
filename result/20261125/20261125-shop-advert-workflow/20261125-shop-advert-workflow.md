# 새 상품 야외 점원 안내 조사·수정 및 요청 처리 절차 변경

사용자는 다음 두 가지를 모두 실제로 수행하라고 요청했다. **이 요청을 읽고 수행하는 세션부터 2번 절차를 적용**한다.

## 1. 새 상품 야외 점원 안내 조사·테스트·수정

원하는 동작: 이전 장들에서 판매하지 않았던 물건을 새로 판매하는 상점이 생기면, 해당 건물로 들어가는 **야외 입구 주변에 점원**이 서서 그 상품을 말풍선으로 알린다. 예를 들어 서주성 도구점에서 중급 인수가 처음 나왔다면 서주성의 도구점 입구 근처에서 “중급인수 팝니다”, “새로운 상품이오”, “어디서도 없던 중급인수 팝니다” 같은 안내를 하고, 말을 걸면 해당 아이템의 설명을 해야 한다. 문구는 사용자의 뜻을 나타내는 예시다. 실제 대사를 쓰거나 수정하기 전 `ver5/docs/story-writing.md`, `ver5/docs/data-speech-style.md`의 사용자 선택 절차·어휘·시대 맥락을 따른다.

- 기존 구현 전체와 각 상점의 판매 목록·해금 조건·장 순서·분기/재방문을 조사해 무엇이 왜 이상하게 적용됐는지 찾는다. **이전 장에서 이미 팔던 상품**이나 같은 상품을 이후에도 계속 홍보하는지, 실제 해당 상점의 입구와 야외에 점원이 있는지, 점원에게 말을 걸 때 안내 대상 상품의 설명이 나오는지, 새 상품이 여러 개/없음/조건부/분기인 경우 등을 확인한다. 사용자 예시를 근거로 특정 상품이 실제로 최초 판매라고 가정하지 말고 실제 데이터를 비교한다.
- 시작점: `ver5/assets/scenario/hero/explore03.json`, `explore08.json`, `explore14.json`, `explore19_ye.json` 등의 `Chatter`, `Talk`, 상점과 출입구. 특히 `explore14.json`의 중급 인수 안내 점원이 상점 내부인지·야외 입구인지 맵과 지역 연결을 실제 게임 캡처로 확인한다. 필요한 경우 `ver5/tools/storydb/storydb.py`를 사용하고 `ver5/docs/presentation-facing.md`를 읽는다.
- 전체 사례를 **정상 / 문제 / 조건·분기 때문에 추가 확인**으로 나눠 파일·지역·상품·최초 판매 근거·입구와 점원·말풍선·대화 내용을 기록한다. 이전 판매 여부는 탐험할 수 있는 장·분기에 따른 도달 가능성을 고려한다.
- 잘못된 사례를 고치고 회귀를 막는 의미 있는 유닛/콘텐츠 테스트를 작성한다. 최소한 최초 판매と 재판매, 새 상품 없음/여러 개, 조건·분기, 올바른 야외 입구와 해당 아이템 설명, 말풍선/대화 일치의 가능한 경계를 검증한다. 데이터 구조만 흉내 내는 테스트가 아니라 실제 상점·탐험 로딩과 기능을 통과하는 경로를 사용한다. 수정 전 실패와 수정 후 통과를 확인할 수 있으면 기록한다.
- 시나리오·탐험 문구와 인물 배치·시선을 바꾸는 경우 프로젝트의 스토리 작성, 자산 및 facing 지침을 적용한다. 사용자 선택이 필요한 문구 초안은 지침대로 준비하고, 그 선택에 의존하지 않는 조사·테스트·구현은 계속한다. 실제 게임에서 대표 사례 전후를 캡처해 시선과 입구를 확인한다.

## 2. 요청 처리 스킬과 테스트 단계 변경

관련 기존 스킬은 `/Users/younwookim/.claude/skills/request-watcher/SKILL.md`, 파일 감시·이동 MCP는 `tools/request_mcp/server.py`다. 실제 실행 중인 처리 경로와 설정을 먼저 확인하고, 미래 요청에서도 아래 절차가 실효적으로 적용되도록 해당 스킬 및 필요한 MCP/설정/문서를 수정한다. 가능한 기존 처리기와 충돌·중복 수행을 방지한다. 다른 작업의 미커밋 변경은 보존한다.

1. 요청이 `request/`에서 `process/<name>/`으로 이동해 작업 중일 때, **1분에 한 번** `process/<name>/`의 진행 기록 Markdown에 실제 시각(Asia/Seoul, 날짜·시간·시간대 명시)과 수행 내용·현재 상태·다음 단계/장애를 기록한다. 경과 시간만으로 진척을 꾸며내지 않는다. 장시간 테스트·도구 실행 중에도 누락되지 않도록 처리기의 동작 방식과 지속성·종료를 검증한다. 여러 요청은 서로의 기록을 덮지 않는다.
2. 구현·작업이 끝나면 요청 Markdown을 `./test/` 아래 요청별 폴더로 **옮긴 뒤 테스트**한다(예: `test/<name>/<name>.md`). `process`의 진행 이력은 조회 가능하게 보존하고, 요청 파일의 이동 상태를 명확히 한다. `./test/`는 프로젝트 루트 `/Users/younwookim/orca/mhdemo1/test/`를 뜻한다.
3. `test/<name>/`의 Markdown에 실행한 각 테스트의 **실제 실행 시각**, 명령/검증 범위, 결과, 실패·버그, 원인, 수정 내용과 재시험 결과를 기록한다. 테스트 중 버그를 발견하면 고치고 재실행한다. 오류를 숨기거나 실행하지 않은 테스트를 통과로 쓰지 않는다. 코드 변경은 요청에 필요한 테스트와 프로젝트가 요구하는 필수 테스트를 모두 실행한다. 비코드 요청은 적용 가능한 검증과 테스트 불필요 이유를 명시한다.
4. **모든 필수 테스트가 실제 통과한 후에만** 요청 Markdown을 `result/YYYYMMDD/<name>/`으로 옮겨 완료 상태로 만든다. 결과 설명·산출물과 테스트 로그를 함께 남기고 원래 요청과 진행·테스트 기록을 연결한다. 실패·미실행·환경상 불가능한 필수 검증이 남으면 `test/`에 머물고 실패 상태와 이유·다음 조치를 기록한다. 완료로 옮기지 않는다.
5. 파일 이동은 중복 소비·동시 처리·같은 이름 충돌·중단 후 재시작을 고려해 안전하게 하고, 기존 요청 기록을 덮거나 잃지 않도록 한다. 스킬의 현재 “process에 계속 남기기”, “요청과 상관없이 커밋 금지” 등과 충돌하지 않게 새 사용자 지시와 기존 프로젝트 규칙 및 명시적 승인 우선순위를 맞춘다. 테스트 프로세스의 시간 기록·성공/실패·이동 조건을 임시 디렉터리 등으로 자동 테스트해 검증한다.

## 이번 작업의 검증·결과

- 이 문서를 받은 즉시 process 진행 기록을 시작하고 매분 기록한다. 절차 변경을 먼저 완성해도 상품 안내 조사·수정을 끝내기 전에는 이 요청을 완료로 표시하지 않는다.
- 기존 `ver5/README.md`, 프로젝트 지침, 관련 코드와 스킬을 읽고 여러 파일 또는 아키텍처 변경 전에 설계 문서를 작성한다. 민감 정보를 기록·커밋하지 않는다.
- 테스트 단계에 들어갈 때 이 요청 문서를 위 규칙대로 `test/`로 옮기고 테스트 실제 시각과 모든 결과를 기록한다. 최종 결과에는 원인, 전수 목록, 수정과 테스트, 전후 게임 캡처, 스킬/MCP 변경·호환성·검증 및 남은 한계를 기록한다. **필수 테스트가 전부 통과한 뒤에만** `result/YYYYMMDD/<name>/`으로 옮긴다.
