# 법정 응징·반계 논의 기록

게임 데이터(ver5/assets/data/*.json)와 Go 코드는 바꾸지 않았다. 아래는 현행 조사와 제안이다.
요청 원문: process/fazheng-reprisal-counterspell-20261124/fazheng-reprisal-counterspell-20261124.md

## 1. 사용자 요청

- (1) 응징: 지계 책략 치명타 + 피격 1회마다 중첩되는 피해 +5%. 중첩은 자기 턴의 직접 공격에만 적용하고 쓴 뒤 초기화한다. 반격 등 다른 반응에는 적용하지 않는다. 부관(deputy) 활용을 고려한다.
- (2) 반계: 물리 반격이 아니어야 한다. 받은 책략을 자신이 다시 시전하되, 자기 병법치(MP)는 쓰지 않는다.

## 2. 현행 코드 사실

### 2-1. 반계 (spell_reflect)

- 데이터: `ver5/assets/data/traits.json` 591행 부근. key `spell_reflect`, 이름 "반계", 설명 "공격 책략을 받으면 같은 책략을 시전자에게 되돌린다.", Cost 500, Effects `{"reflect": 1}`.
- 같은 계열: `counter_scheme`(역계, 600행 부근, Requires spell_reflect, `reflect_status` 1 - 해로운 상태이상 책략을 되돌린다).
- 효과 키 상수: `ver5/internal/content/vocab.go` 72행 `FxReflect = "reflect"`, 73행 `FxReflectStatus`.
- 발동 위치: `ver5/internal/core/combat.go` 950행 `apply` 클로저 안, 공격 책략(`s.Kind == content.KindMagic`) 분기.
  - 974~976행: `if !derived && e.has(q, content.FxReflect) && q.HP > 0 && u.HP > 0 && !confused(q) { e.strike(q, u, s, blow{share: 1, derived: true}) }`
  - 즉 피격자 q가 같은 스킬 s를 시전자 u에게 다시 `strike`한다. 명중·치명·데미지 계산은 q 기준(`damage(q, u, s)`는 `strike` 안에서 `u`가 공격자 인자로 들어간다. 즉 strike(q,u,...)는 공격자가 q이다).
  - `derived: true`라서 되돌려진 책략은 다시 되돌아가지 않는다(무한 핑퐁 방지).
- 병법치 소모: 소모는 `useSkill`에서만 한다(`ver5/internal/core/combat.go` 701~703행, `u.MP = max(0, u.MP-n)`). 반계 경로는 `useSkill`을 거치지 않고 `strike`를 직접 부르므로 **반계된 책략은 병법치를 소모하지 않는다.** 이미 사용자 의도와 맞는다.
- 능력치: 데미지는 `damage()`(combat.go 28행)가 공격자의 지력(`a.Mind`)과 `s.MagicCoeff`로 계산한다. 반계에서는 공격자가 q이므로 **반계하는 장수 자신의 지력**이 쓰인다. "자신의 병법치(지력)로 시행"이라는 요청과 맞는다.
- 역계 경로(983~985행)는 상태이상 책략을 q가 아니라 u로 되돌린다(`q = u`).

### 2-2. 현행 반계는 "물리 반격"이 아니다

- 반계는 `spell()`의 책략 분기에서 처리된다. 물리 반격(counterBack/strikeBack, combat.go 491~547행)과 경로가 다르다.
- 따라서 요청 (2)의 "물리 반격처럼 보이면 안 된다"는 조건은 **현행 구조에서 이미 충족**된다. 새로 만들 필요가 없다.

### 2-3. 확인이 필요한 현행 동작 (버그 가능성)

- 974행 반계 조건에 **명중 여부(hit) 검사가 없다.** `strike()`(combat.go 297행)는 빗나가면 `emit("miss")` 후 `return 0,false,false`(320~325행)로 끝나지만, `apply`는 그 뒤에도 974행을 실행한다. 코드만 보면 **빗나간 책략도 되돌아간다.**
  - 의도인지 실수인지 확인이 필요하다. 의도가 아니면 `hit` 조건을 추가하는 1줄 수정 후보다(사용자 승인 후).
- 반계 대상 q가 `immune`(화덕성군 등)으로 0 피해를 받은 경우도 `strike`가 `hit=true`로 반환해 되돌아갈 수 있다(307행, 304행 분기). 이것도 확인 필요.

### 2-4. 응징 관련 기존 코드

- 이름 충돌: `traits.json` 63~72행의 `retaliate`가 이미 "응징"이다(물리 공격에 모두 반격, 책략 무반응). 새 응징은 **다른 이름**이 필요하다(예: 보복, 되갚음 - 설계 결정 필요).
- 피격 처리: `hurt(v, n, u)`(combat.go 270행)가 HP 감소의 공통 지점이다. 응징 중첩을 쌓으려면 피격 이벤트를 여기서 세거나, `strike`에서 `hit`을 기준으로 셀지 정해야 한다.
- 상태 저장: `Unit.Status map[string]Status`(types.go 21~24행, `Turns, Value int`, `Source string`). 턴마다 정리되는 로직이 있다(combat.go 1252~1307행 근처, `delete(u.Status, "counter")` 등).
- 중첩 수치 적용: `fx()`(engine.go 360행)는 상태의 `Value`가 아니라 `content.StatusEffects[id][key]`라는 **고정 값**만 더한다. 그러므로 "중첩 × 5%"는 기존 fx로 표현할 수 없고 **새 코드가 필요**하다. `Value`를 읽어 `damage()` 또는 `boost()`(combat.go 108행)에 곱하는 분기가 필요하다.
- 기존 `Value` 활용 예: `applyStatus`(combat.go 257~261행)는 부호가 있는 스탯 상태에만 쓰인다. 응징 중첩에 `Value`를 쓰는 선례는 없다.
- 자기 턴에만 적용: `counterBack`/`strikeBack`(반격 경로)과 직접 공격 경로(`attackOn` 계열)가 나뉘어 있으므로, "직접 공격인지"를 구분하는 플래그(`derived`, `counter`)가 이미 있다(`blow` 구조체 289~292행: `share`, `derived`, `second`). 응징 적용 조건은 `!b.derived && !counter`로 표현할 수 있다. 다만 `counter` 인자는 `strikeBack`에 있으므로 확인이 필요하다.
- 초기화: 응징을 쓴 뒤 0으로 만드는 지점은 "자기 턴 직접 공격 후"가 된다. `useSkill`/공격 명령 처리 끝(api.go 근처)이 후보다.

### 2-5. 지계 치명 (지공) 관련

- 지공 후보 키: `"crit:earth": 1`. 처리는 `critForced()`(combat.go 190~199행)의 책략 분기 `e.fx(u, content.FxCritElement+s.Element)`에서 이미 된다. 코드 변경 없이 데이터 항목 추가로 가능하다(앞선 design.md 확인).
- 추살과의 차이: `FxCritWounded`(vocab.go 19행)는 책략에도 적용된다(combat.go 192행 첫 조건).

### 2-6. MP 소모 지점 (한 곳인지)

- 병법치 소모는 `useSkill`(combat.go 701~703행) 한 곳이다. 반계는 여기를 건너뛴다.
- 비용 계산: `cost()`(rules.go 264행)가 백출(`FxCostHalf`)을 반영한다. 소모 가능 여부는 rules.go 497행(`payable`)과 api.go 904행(AI 후보 필터)에서 본다.
- 흡수: 격파(`FxAbsorbMana`, vocab.go 123행)는 `absorbMana`(combat.go 744행)에서 적의 남은 MP를 가져온다. 법정에게 격파를 주면 적 처치 시 MP가 법정에게 간다. 반계로 **MP 소모 없이 시전한 책략**과 격파(MP 획득)는 서로 간섭하지 않는다(MP를 쓰지 않으므로).

### 2-7. 부관(deputy) 특성

- 부관 지정: `formation.go`(10~77행), 부관 해제/교체 로직은 `engine.go` 664~668행 근처.
- 특성 합산: `fx()`는 `e.traits(c)`를 쓰고(engine.go 369행 `fxOf`), `ownFx()`(engine.go 380행 근처)는 "부관의 특성을 뺀" 자기 특성만 합친다. 이를 보면 **부관 특성은 기본적으로 합산에 포함된다**(engine.go 352행 `d := e.char(c.Deputy)` 분기 참고, 정확한 조건은 미확인).
- 부관 전용 효과 키: `FxDeputyPlus`(vocab.go 41행, "부관의 능력치가 이만큼 더 높게 섞인다"). 부관 특성이 주장에게 전달되는지는 기존 결정(design 문서)과 맞는다.
- 응징에 부관을 쓰는 아이디어: 법정이 부관으로 주장(예: 유비)에게 응징 특성을 주면, 주장이 피격당할 때 중첩이 쌓이고 주장 자신의 직접 공격에 쓰인다. 구성 자체는 가능하다. 단 "피격을 쌓는 주체"가 특성 보유자(법정)인지 주장인지 정해야 한다. 상태(Status)는 주장 유닛에 붙으므로 **주장 유닛이 피격할 때 쌓이게 하면** 부관 전달 구조와 맞는다.

## 3. 기능별 구현 가능성

| 항목 | 현행 코드로 가능? | 필요한 작업 |
|---|---|---|
| 지공(지계 명중 시 치명) | 가능 (데이터만) | traits.json에 `"crit:earth": 1` 특성 추가 |
| 반계(받은 책략 재시전, MP 없음, 물리 반격 아님) | **이미 구현됨** (combat.go 974행, `spell_reflect`) | 빗나감 되돌림 여부 확인 후 필요 시 hit 조건 추가 |
| 응징 중첩 피격 +5% (직접 공격에만, 쓰고 초기화) | 불가 (고정 상태 값만 fx가 읽음) | 새 상태 키와 피격 시 중첩 증가, 자기 턴 직접 공격에서만 `damage()` 또는 `boost()`에 곱하기, 사용 후 초기화 |
| 응징을 부관으로 전달 | 구조상 가능 (특성 합산·부관 지정 존재) | 피격 주체를 주장으로 할지 정하고 테스트 |
| 응징 이름 | 충돌 (`retaliate`가 "응징") | 다른 이름 결정 |

## 4. 열린 설계 질문 (사용자 확인 필요)

1. 응징의 이름: 기존 `retaliate`가 "응징"이므로 새 이름을 정해야 한다(보복, 되갚음 등).
2. 반계 빗나감: 빗나간 책략도 되돌아가는 것이 의도인가? 기본은 "명중한 책략만 되돌린다"로 보고 수정 후보로 둔다.
3. 응징 피격 기준: 명중 피격만 세는가, 빗나간 공격·0피해(면역)·범위 피해·다단 공격의 각 타수를 모두 세는가?
4. 응징 최대 중첩: 상한을 둘 것인가? (예: 5중첩 = +25%)
5. 응징 소모 시점: 공격이 빗나가거나 대상이 없어도 쓴 것으로 칠 것인가?
6. 응징 적용 대상: 주장 피격을 쌓는 구조(부관 전달)를 쓸지, 법정 자신의 피격만 쌓을지?
7. 적 턴 중 직접 행동은 해당 없음(자기 턴 직접 공격만)으로 충분한가?
8. 응징에 쓰는 계수: 지계 책략에만 적용할지, 모든 직접 공격에 적용할지?
9. 법정 특성 배정과의 충돌:
   - 격파는 사용자 결정으로 법정에게 준다(design 문서). 격파는 MP 흡수라 반계/응징과 간섭하지 않는다.
   - 화공 배정: 허사는 심모→화공, 황보숭은 화신→화공으로 교체하기로 결정된 상태다(result/20261124/firecraft-officer-decisions-20261124/result.md). 법정의 화공 배정(fazheng-jiangwan-feiyi-design 문서)은 아직 확정되지 않았으므로, 지공을 넣을 때 화공과 역할이 겹치는지 정해야 한다.
   - 지공과 심모/화신이 같이 있으면 치명이 겹친다(design 문서 기록과 같다).

## 5. 미검증 항목

- 반계가 빗나감에도 되돌아가는지: 코드 읽기로만 확인했다. 실제 동작은 테스트나 전투 시뮬레이션으로 확인해야 한다(실행하지 않았다).
- 부관 특성이 `fx()`에 어떻게 합산되는지: engine.go 352행 분기의 정확한 조건은 읽지 않았다.
- `counter` 인자가 직접 공격과 반격을 어떻게 구분하는지: `strikeBack`의 `counter` 인자 흐름은 전체를 읽지 않았다.
- 지공 수치(거암 계수 2 기준 치명 3배 등)와 응징 +5%의 밸런스: 계산 예일 뿐이며 시뮬레이션이 필요하다.
- 법정의 실제 전투 배정 여부(Traits, Learn 목록)는 characters.json 기준으로 확인하지 않았다.

## 6. 진행 경로 (제안)

1. 사용자가 응징 이름과 위 질문 2·3·6번에 답한다.
2. 반계 빗나감 여부를 확인한다. 의도가 아니면 974행에 hit 조건을 추가하는 작은 수정을 승인받는다.
3. 지공은 데이터 한 항목으로 먼저 넣고 자동 전투에서 체감을 본다.
4. 응징은 (a) 상태 키 정의, (b) 피격 시 중첩 증가, (c) 자기 턴 직접 공격에서 곱하기·초기화 순서로 구현한다. 테스트는 "반격에는 적용 안 됨", "직접 공격 후 초기화", "부관 전달 시 주장 피격 중첩"의 세 가지를 둔다.
5. 데이터·코드 변경은 사용자 승인 후에만 진행한다.
