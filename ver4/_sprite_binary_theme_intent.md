# 스프라이트 바이너리 및 테마 팔레트 구조 변경 의도

## 목적

`tools/doteditor`에서 만든 스프라이트의 태그와 테마색 정보를 게임까지 보존한다.
같은 스프라이트를 사용하면서 유닛별 진영색, 옷색, 말 피부색·갈기색·안장색 등을
독립적으로 지정할 수 있도록 ver4의 에셋 빌드와 로딩 구조를 변경한다.

YAML은 편집 원본으로 유지하고, 게임에서는 YAML을 빌드한 바이너리를 읽는다.
핵심은 파일 확장자를 바꾸는 것이 아니라 픽셀의 색상 의미를 런타임까지 전달하는 것이다.
이 문서는 변경 의도를 기록하며, 구현 완료를 의미하지 않는다.

## 현재 구조와 한계

- doteditor는 픽셀별 태그와 태그별 색상을 관리한다. 진영색, 테마 A/B/C,
  말 피부·갈기·안장 등의 태그로 부분별 색상을 변경할 수 있다.
- `tools/doteditor/apply.py`는 YAML의 팔레트와 픽셀 인덱스로 PNG를 생성한다.
  게임용 결과에는 픽셀별 태그와 테마 팔레트 정보가 전달되지 않는다.
- `internal/gui/assets.go`는 PNG에서 정해진 파란색 4개와 일치하는 픽셀을
  진영 팔레트로 치환한다. 색상의 의미가 아닌 RGB 일치에 의존한다.
- 에디터에서 바꾼 옷색·말색을 PNG로 다시 빌드하면 게임에 반영할 수 있지만,
  게임에서 같은 스프라이트의 옷색·말색을 유닛별로 지정하는 구조는 없다.

## 목표 흐름

```text
tools/doteditor/units/*.yaml — 편집 원본
  → 빌드: 프레임·태그·기본 팔레트를 바이너리로 변환
  → assets/ 아래 게임용 바이너리 저장
  → 게임에서 바이너리 로딩
  → 기본 팔레트에 진영색·유닛별 외형 설정 적용
  → 스프라이트 시트 생성 및 캐싱
  → 기존 애니메이션·전장 렌더링에서 사용
```

## 바이너리에 보존할 정보

| 정보 | 용도 |
|---|---|
| 포맷 식별자와 버전 | 파일 검증 및 형식 변경 대응 |
| 유닛 식별자, 셀 크기, 기준점 | 에셋 식별과 배치 |
| 방향, 애니메이션 구성, 프레임 시간, 반복 여부 | 기존 동작 재생 |
| 원본 팔레트와 픽셀별 팔레트 인덱스 | 태그가 없는 픽셀의 원본색 보존 |
| 태그 정의, 태그별 기본색, 픽셀별 태그 번호 | 의미에 따른 부분별 색상 변경 |
| 픽셀 투명도 | 기존 실루엣과 반투명 표현 보존 |

구체적인 필드 배치, 정수 크기, 압축 여부, 확장자는 구현 설계에서 결정한다.
YAML 전체를 그대로 직렬화하기보다 게임에 필요한 데이터를 명시적으로 저장한다.
편집용 비교 레이어 등은 런타임 데이터에서 제외한다.

## 색상 적용 원칙

1. 태그가 없는 픽셀은 원본색을 유지한다.
2. 태그가 있는 픽셀은 해당 태그의 최종 팔레트 색상을 사용한다.
3. 같은 RGB라도 태그가 다르면 독립적으로 변경할 수 있어야 한다.
4. 진영색, 테마 A/B/C, 말 관련 색상은 각각 독립적으로 지정한다.
5. 색상을 바꿔도 픽셀 투명도는 유지한다.
6. 기본 팔레트에 진영 설정과 유닛별 외형 설정을 적용한다.
   동일 태그에 설정이 겹칠 때의 우선순위는 구현 설계에서 명시한다.

예를 들어 같은 기병 스프라이트를 아군은 초록 진영색과 갈색 말로,
적군은 노랑 진영색과 검은 말로, 특정 장수는 소속 진영색과 고유 옷색·흰 말로 표현한다.

## 런타임 및 변경 범위

- 색상 적용은 매 프레임 수행하지 않고 최초 사용 또는 외형 변경 시 수행한다.
- 생성한 시트는 스프라이트 식별자와 최종 팔레트를 기준으로 캐싱한다.
  현재의 진영만을 기준으로 한 캐시로는 유닛별 외형 차이를 표현할 수 없다.
- 변경 범위는 doteditor 유닛의 빌드, 바이너리 로더, 팔레트 적용과 캐싱,
  새 비전투 스프라이트의 장면 연결 및 행동 명령 통합이다.
- 기존 `Frame()` 호출과 애니메이션·전장 렌더링 인터페이스는 가능한 한 유지한다.
- 그림자 생성과 로딩은 새 에셋 경로에서도 기존 동작을 유지하도록 연결한다.
- 런타임 에셋은 `assets/` 아래에 두고, doteditor YAML은 편집 원본으로 유지한다.
- YAML 원본이 없는 기존 스프라이트의 전환 범위와 과도기 로딩 방식은 별도로 결정한다.
  기존 RGB 치환을 제거하는 시점도 이 전환 범위에 맞춘다.

## 새 비전투 스프라이트와 장면 행동 통합

새 비전투 도트 `<id>_noncombat`을 장면용으로 연결하고, 기존 비전투 행동 명령은
`action` 하나로 통합한다. 이는 확정된 변경 방향이며, 기존 행동별 도트를 추가 제작하지 않는다.

### 새 비전투 도트의 구조

- 원본은 NW·SW 두 방향이며, 방향마다 `idle` 1장, `walk` 2장, `action` 1장을 갖는다.
- NE·SE는 각각 NW·SW를 좌우반전하여 만든다. 기준점과 픽셀별 태그·투명도도 함께 처리한다.
- 걷기는 `idle → walk 0(왼발 앞) → idle → walk 1(오른발 앞)` 순서로 재생한다.
- `action`은 장수별 고유 자세 한 장이다. 유비는 팔 벌려 맞이하기,
  관우는 수염 쓰다듬기이며, 같은 명령을 받아도 각 장수의 고유 자세를 보여 준다.
- 기병 장수도 비전투에서는 말에서 내리고 무기를 제거한 차림이다.
- 비전투 도트에도 동일한 태그 기반 팔레트를 적용하여 진영색과 고유 옷색을 독립적으로 유지한다.

### 기존 명령 처리

기존 장면의 비전투 동작 `talk`, `salute`, `toast`, `surprise`, `nod`, `exhausted`는
모두 `action`으로 통합한다. 예를 들어 포권 장면과 건배 장면 모두 장수의 고유
`action` 자세를 사용하며, 상황의 의미는 대사와 장면 연출로 전달한다.

- `assets/scenes.json`의 비전투 행동 지시와 게임의 자동 대화 동작 선택을 함께 변경한다.
  데이터만 바꾸고 코드에서 기존 동작을 요청하는 경로를 남기지 않는다.
- 기존 명령 이름을 각각 유지하는 대신 장면 데이터와 실행 코드에서 `action`을 사용한다.
- `action`은 반복 재생하지 않는 자세로 처리하고, 지정된 재생 시간이 끝나면 `idle`로 복귀한다.
- 대기와 걷기는 각각 `idle`, `walk`로 유지한다. 이동, 방향 전환, 말풍선,
  대사, 이모트, 대기 시간, 장면 효과는 이 행동 통합의 대상이 아니다.
- 전투 스프라이트의 `attack`, `hit`, `block`, `exhausted` 등은 전투 동작으로 유지한다.
  같은 이름의 명령이라도 비전투 장면 동작인지 전투 도트의 연출인지 구분한다.

### 장면 연결과 검증

- 현재 장면의 기본 선택은 `civ_<id>`이며, 새 `<id>_noncombat`은 인덱스에 있어도
  자동 선택되지 않는다. 새 비전투 도트가 있는 장수는 이를 사용하도록 선택 경로를 변경한다.
- 새 비전투 도트가 없는 장수·엑스트라의 처리 방침은 에셋 전환 범위에 맞춰 결정한다.
- 바이너리 빌드에서도 좌우반전과 걷기 프레임 재사용 규칙을 보존한다.
  프레임을 펼쳐 저장할지 참조로 표현할지는 구현 설계에서 결정한다.
- 도원결의·마을·진영 등 기존 장면에서 모든 비전투 행동이 `action`으로 실행되고,
  동작 누락이나 재생 대기로 장면 진행이 멈추지 않는지 검증한다.
- 유비와 관우가 같은 `action` 명령으로 서로 다른 고유 자세를 보여 주는지,
  재생 후 대기로 복귀하는지, 걷기 순서와 네 방향 표시가 올바른지 검증한다.

## 구현 전 결정 및 검증할 사항

- 바이너리 형식, 버전 정책, 잘못된 크기·인덱스·태그 및 잘린 파일의 검증 방법.
- 유닛별 외형 설정의 저장 위치와 기본값, 팔레트 적용 우선순위.
- 전투 유닛과 비전투 유닛의 전환 범위 및 기존 PNG 에셋 처리 방침.
- 기본 팔레트로 렌더링했을 때 기존 결과와 색상·투명도·방향·동작이 일치하는지 검증.
- 진영색·옷색·말색 변경이 지정한 태그에만 적용되는지 검증.
- 서로 다른 외형의 캐시가 섞이지 않고 동일 외형은 재사용되는지 검증.
- 로딩 시간, 팔레트 적용 비용, 메모리 사용량을 측정한다.
  바이너리 전환만으로 성능이 개선된다고 가정하지 않는다.
