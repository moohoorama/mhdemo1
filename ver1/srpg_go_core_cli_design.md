# 삼국지 SRPG Go 코어와 CLI 설계

작성일: 2026-10-01. 상태: 구현 설계 초안.

> 최신 사용자 결정과 다음 구현 범위는 §16을 우선한다. 아래 CLI 초안의 승리 경험치·격퇴 고정 경험치 등과 충돌하면 §16이 우선한다.

이 문서는 Go와 ECS로 공통 게임 코어를 구현하고, CLI에서 도원결의부터 호로관 전투까지 진행하는 방법을 정의한다. 이후 Ebitengine 화면을 연결해도 규칙·AI·저장 데이터를 재사용한다. 시작 화면은 **시작하기·불러오기·설정·종료**를 제공하며, 시나리오와 전투 도중 현재 진행을 저장하고 재개할 수 있다.

기준 문서는 [삼국지 SRPG 통합 기획서](srpg_complete_design.md)이다. 1부의 확정 규칙을 우선한다. 이 문서의 기술 구조·메뉴·저장 방식은 구현 제안이며, 2부에서 가져온 초기 병종·수치·맵 크기·적 프로필·승리 조건은 플레이 검증 전 임시 콘텐츠다. 원문에서 미정인 사항을 확정 사실로 취급하지 않는다.

## 1. 구현 범위

첫 버전은 다음 흐름을 끝까지 지원한다.

```text
시작 메뉴
  → 도원결의 대사와 출전 준비
  → B01 황건적의 난
  → 승리 결과와 간옹 합류
  → 동탁 타도군 일어나다 대사와 출전 준비
  → B02 사수관 전투
  → 승리 결과
  → 호로관 추격 시나리오에서 손건의 고정도 전달
  → 고정도를 포함한 출전 준비
  → B03 호로관 전투
  → 승리 결과와 초반 캠페인 완료
```

유비·관우·장비는 Lv1로 시작한다. 간옹은 첫 전투 승리 후 독립 장수로 합류해 두 번째 전투부터 출전할 수 있다. 손건의 고정도 전달은 손건의 아군 합류를 의미하지 않는다. 초반 세 전투에는 승급·부관·고급 병종·전설 장비를 공급하지 않는다.

첫 버전은 일반 공격, 초기 병법과 특성, 이동·지형·ZOC, 아이템, 경험치·특성 학습, 장비 준비, 적 AI, 승패, 결과 이월을 구현한다. 실제 초반 콘텐츠에서 접근할 수 없는 후반 병법·특성·승급·부관은 확장 경계만 마련한다.

호로관 승리 뒤에는 완료 상태와 최종 편성을 조회·저장할 수 있다. 다음 전투를 임의로 생성하지 않는다. 패배 시에는 패배 화면에서 불러오기·출전 직전 상태로 재도전·시작 메뉴로 이동을 제공한다. 재도전은 출전 직전 체크포인트를 복원하며, 패배 전 소비·성장·난수 상태를 일부만 유지하지 않는다.

## 2. 책임과 의존 관계

| 구성 | 책임 | 허용하지 않는 역할 |
|---|---|---|
| core | 게임 상태, ECS, 명령 검증, 전투·성장·시나리오 판정 | 표준 입출력, 파일 접근, Ebitengine 참조 |
| content | 정의 데이터 로딩과 ID·수치·호환성 검증 | 실행 중 게임 상태 변경 |
| ai | 읽기 전용 관찰과 가능한 행동으로 명령 선택 | 상태 직접 수정, 별도 피해 공식 |
| session | 차례별 사람·AI 요청 조율, 메뉴, 저장 요청, 실행 경계 | 피해·명중 규칙 재구현 |
| cli | 텍스트·JSON 입출력, 명령 파싱, 오류 표시 | 전투 판정, AI 정책 소유 |
| client | 향후 Ebitengine 입력·화면·소리·연출 | 연출 시간에 따른 규칙 변경 |
| storage | 저장 슬롯, 설정 파일, 안전한 쓰기와 읽기 | 콘텐츠 보상 지급 |
| sim | 반복 실행과 통계 수집 | 규칙 우회 |

```text
사람 → CLI / Ebitengine → Session → Core
                             ↑       ↓
                             AI ← 관찰·행동 후보

Session ↔ Storage
Core ← 검증된 Content
Core → 조회 결과·게임 이벤트 → CLI / Ebitengine
```

CLI와 Ebitengine은 입출력 어댑터이고 AI는 행동 선택 정책이다. Session이 현재 차례에 맞춰 명령을 받아 Core에 제출한다. 모든 명령은 동일한 권한·자원 검증을 통과한다. 내부 AI는 Go API로 호출하고, 외부 AI는 CLI JSON 프로토콜로 연결할 수 있다.

## 3. 패키지 구성

```text
cmd/srpg-cli/       사람용·JSON CLI 진입점
cmd/srpg-sim/       반복 시뮬레이션 진입점
cmd/srpg/           향후 Ebitengine 진입점
internal/core/      API, ECS 상태, 규칙, 효과 처리, 시나리오
internal/content/   로딩, 스키마와 참조 검증
internal/ai/        돌격·원거리·책략 정책
internal/session/   화면 상태, 제어자, 실행 경계
internal/storage/   슬롯·설정·파일 교체
internal/cli/       파싱·텍스트 표시·JSON 프로토콜
internal/sim/       시드별 실행·통계
internal/client/    향후 그래픽 클라이언트
assets/content/     실행용 장수·병종·맵·시나리오 JSON
assets/             실행용 이미지·폰트·음악
tools/spritetool/assets/  원본 artwork
```

콘텐츠 파일은 개발 중 외부 파일로 읽되 검증을 통과한 불변 정의로 Core에 전달한다. 배포 시 포함 방식은 별도 결정한다. 사용자 저장·설정은 운영체제의 사용자 데이터 디렉터리에 보관하며 설치 폴더와 assets에 쓰지 않는다.

현재 작업 폴더에는 통합 기획서만 존재한다. 참조된 README.md와 srpg_content_data.json은 없으므로 실제 구현 전에 원본 콘텐츠를 확보하거나 기획서의 초반 정의를 구조화해야 한다. sprite 작업 시에는 저장소 지침의 artwork 가이드와 대상 설정을 먼저 읽는다.

## 4. ECS 상태 모델

ECS 라이브러리는 Ark를 우선 검토하되 Core API가 해당 라이브러리 타입을 외부에 노출하지 않도록 한다. 시스템 실행 순서는 게임이 명시적으로 정의한다.

| 엔티티 | 컴포넌트 | 수명 |
|---|---|---|
| 장수 | OfficerRef, Growth, LearnedTraits, Equipment | 캠페인 전체 |
| 출전 부대 | UnitRef, Faction, Position, Resources, ActionBudget, Statuses | 해당 전투 |
| 장비 인스턴스 | EquipmentDefRef, Owner | 캠페인 전체 |

Growth에는 레벨·경험치·특성치를 기록한다. UnitRef는 주장 장수의 영구 ID와 병종 ID를 참조한다. 이후 부관 관계를 추가할 수 있으나 초반에는 사용하지 않는다. Resources는 현재 병력·병법치, ActionBudget은 이동·행동·일반 공격 사용 여부를 각각 보관한다. 일반 공격 상한과 행동 소모를 하나의 boolean으로 합치지 않는다.

장수 정의, 병종 정의, 특성·병법·장비 효과 정의는 콘텐츠 저장소에 둔다. 특성마다 개별 컴포넌트를 만들지 않고 출처별 제공 목록을 합산해 활성 특성·사용 병법·학습 자격을 산출한다. 활성 특성은 같은 ID당 한 번 적용하고, 학습 자격은 버프 출처를 제외한다.

맵 타일은 고정 격자 데이터, 점유 정보는 부대 Position에서 재구축 가능한 인덱스로 관리한다. 캠페인 진행, 창고, 전투 차례, 시나리오 커서, 난수 상태는 World 수준 상태로 둔다. 모든 값을 엔티티로 만들 필요는 없다.

ECS 내부 핸들은 저장의 영구 ID로 사용하지 않는다. 장수·부대·장비마다 안정적인 도메인 ID를 두고 불러오기 때 ECS 핸들로 다시 매핑한다. 조회 캐시·파생 전투 수치·점유 인덱스는 복구 시 다시 계산한다.

## 5. 게임 상태와 메뉴 상태

게임 상태와 Session의 표시 상태를 구분한다.

| 게임 상태 | 저장되는 내용 |
|---|---|
| Scenario | 시나리오 ID, 현재 노드·선택 대기, 지역 변수, 편성·창고 |
| Battle | 스테이지, 전체 부대, 차례·행동 예산·상태이상·난수 |
| BattleResult | 승패, 확정 보상·성장 결과, 결과 표시 진행 |
| CampaignComplete | 초반 캠페인 완료, 최종 성장·소지품 |

Session 표시 상태는 Title, Playing, PauseMenu, SaveMenu, LoadMenu, Settings, ExitPrompt로 구성한다. 일시정지 메뉴를 열어도 게임 상태가 시나리오에서 전투로 바뀌거나 턴이 진행되지 않는다. Title에는 진행 중 게임이 없어도 된다.

### 5.1 시작 메뉴

```text
1. 시작하기
2. 불러오기
3. 설정
4. 종료
```

- 시작하기: 새 캠페인과 시드를 생성하고 도원결의 첫 노드를 표시한다. 기존 저장 파일을 삭제하지 않는다.
- 불러오기: 슬롯 목록을 표시한다. 저장이 없으면 안내하고 메뉴로 돌아간다. 유효한 저장을 선택하면 기록된 단계로 재개한다.
- 설정: 전역 설정을 변경하고 시작 메뉴로 돌아간다.
- 종료: 파일 작업을 완료하고 프로세스를 종료한다.

진행 중 메뉴에서 시작 화면으로 이동하려면 저장 후 이동·저장 없이 이동·취소를 제공한다. 다시 시작하기를 누르면 새 캠페인을 생성한다.

### 5.2 진행 중 메뉴

시나리오·전투·결과 화면에서 menu 명령으로 계속하기·저장하기·불러오기·설정·시작 메뉴·종료를 연다. 저장 화면에는 10개 수동 슬롯과 자동 저장 슬롯을 제공한다는 초안을 사용한다. 기존 수동 슬롯 덮어쓰기는 사람용 CLI에서 확인한다.

변경된 게임 상태가 마지막 저장과 다르면 종료와 다른 저장 불러오기 전에 저장·진행 포기·취소 선택을 제공한다. 저장 실패 시 진행 포기를 자동 선택하지 않는다. JSON 모드는 대화형 확인 대신 overwrite와 discard_current 필드로 의도를 명시한다.

### 5.3 설정

첫 CLI 버전은 텍스트 표시 속도, ANSI 색상, 로그 상세도, AI 자동 진행 또는 한 명령씩 진행을 지원한다. 향후 음량·해상도·전체화면·키 설정은 그래픽 클라이언트에서 추가한다. 사용하지 않는 설정을 CLI의 작동 기능처럼 표시하지 않는다.

설정은 별도 파일에 저장하며 기존 게임 저장을 불러와도 현재 사용자 설정을 유지한다. 난이도·콘텐츠 버전·AI 정책·초기 시드는 게임 실행 구성으로 저장하고 전역 표시 설정과 섞지 않는다.

## 6. 시나리오 진행

시나리오 정의는 안정적인 ID를 가진 노드와 전이로 구성한다. 지원 노드는 Dialogue, Choice, GrantReward, JoinOfficer, Preparation, StartBattle, EndCampaign이다. 대사 문자열을 effect 코드처럼 해석하지 않는다.

Dialogue에서는 현재 대사 전체를 조회할 수 있고 next 명령으로 다음 노드에 이동한다. 타이핑 연출 위치는 게임 판정 상태가 아니므로 불러오기 후 현재 대사를 처음부터 온전히 표시한다. Choice에서는 선택지 ID와 현재 선택 대기를 저장하며 선택 확정 전 효과를 적용하지 않는다.

GrantReward·JoinOfficer 같은 자동 노드는 플레이어 대기 노드까지 원자적으로 처리한다. 노드 효과, 실행 기록, 다음 커서를 함께 확정한다. 이미 실행한 이벤트 키를 다시 만나면 지급·합류를 반복하지 않는다. 저장에는 커서와 실행 기록을 모두 포함한다.

Preparation에서는 출전 장수와 장비를 확인·변경한다. 전투에서 장비 조작·부관 임명을 허용하지 않으며, 시나리오에서는 소비아이템 사용·특성치 학습을 허용하지 않는다. 이 권한은 UI 표시뿐 아니라 Core에서 검사한다.

간옹 합류는 B01 승리 전이에서 한 번 적용한다. 고정도는 B02 보상 정의와 시나리오 지급을 중복 실행하지 않고 손건 전달 노드에서 한 번 창고에 지급한다는 구현안을 사용한다. 자동 장착은 하지 않고 호로관 출전 준비에서 사용자가 장착한다. 이 수령·장착 정책은 원문의 미정 사항에 대한 제안이다.

## 7. 초반 콘텐츠와 전투 전이

다음 수치는 통합 기획서 2부의 초안에서 가져온다.

| 전투 | 맵 초안 | 출전 상한 | 주요 적과 고정 레벨 | 승리 조건 초안 |
|---|---|---|---|---|
| B01 황건적의 난 | 18×14, 초원·마을 | 3 | 정원지 4, 등무 2, 장각 2 | 장각 격퇴 |
| B02 사수관 전투 | 20×16, 초원·성 | 4 | 화웅 6, 호진 4 | 화웅 격퇴 |
| B03 호로관 전투 | 22×18, 황무지·성·성내 | 4 | 여포 9, 이유 7, 이각 7 | 여포 병력 40% 이하 또는 격퇴 |

일반 적 부대는 B01 4부대, B02·B03 각각 6부대에 주요 적을 별도로 추가하는 원문 초안을 사용하되 실제 타일 배치는 별도 데이터로 작성한다. 아군 레벨을 읽어 적 레벨을 조정하지 않는다. B03 여포는 기본 경기병이며 전설 보물을 제공하지 않는다.

초기 병종·장비는 유비 경보병, 관우·장비 경기병, 간옹 Lv2 궁병이라는 2부 초안을 사용한다. 유비·관우·장비 Lv1과 간옹의 합류 시점만 확정 규칙이다. 개별 고유 특성·학습 목록·소모품·고정도 효과는 원문 정의와 호환되도록 콘텐츠에 명시한다.

전투 시작 명령은 준비 상태를 검증하고 출전 직전 재도전 체크포인트를 만든 뒤 전장 부대를 생성한다. 시작 병법치는 최대의 50%를 내림한 값이다. 초기 아군 병력 완전 회복과 일반 퇴각 장수의 다음 시나리오 복귀는 초반 구현 제안으로 둔다.

턴은 아군 진영 → 적 진영 → 다음 라운드 순서로 진행하는 구현안을 사용한다. 아군 진영에서 사용자가 행동할 부대를 선택한다. 적 진영에서 Session이 안정적인 부대 순서로 AI를 호출한다. 이동·행동 순서는 자유롭게 허용하되 이동은 분할하지 않고 확정 후 되돌리지 않는 초안을 채택한다. 공격 여부와 관계없이 수동 대기할 수 있다. 회복과 버프 종료는 각 부대의 자기 턴 시작·종료 기준으로 정의하고 프레임과 연결하지 않는다.

유비 전투불능 또는 출전 아군 전원 전투불능은 패배라는 제안을 사용한다. 한 명령의 모든 효과가 끝난 뒤 판정하며 같은 명령에서 승패 조건이 함께 성립하면 패배를 우선한다. 승리 여부를 타격마다 중복 확정하지 않는다. 턴 제한은 스테이지에 명시된 경우에만 적용한다.

전투 결과 확정 시 경험치·레벨·특성치·소모품·창고·진행 플래그를 원자적으로 갱신한다. 결과 화면의 계속하기는 표시와 다음 전이만 수행하며 보상을 다시 지급하지 않는다. B01 이후 간옹, B02 이후 고정도, B03 이후 완료 상태가 각각 고유 이벤트 키를 갖는다.

## 8. 명령 처리와 시스템 순서

외부 입력은 타입이 있는 명령으로 변환한다. 게임 명령에는 AdvanceScenario, ChooseOption, Equip, Unequip, SetDeployment, StartBattle, Move, Attack, UseSkill, UseItem, LearnTrait, WaitUnit, EndFaction, ContinueResult가 있다. Save·Load·Settings·Quit은 Session 명령이며 전투 행동을 소비하지 않는다.

Core는 한 번에 하나의 명령을 처리한다.

1. 진행 단계, 차례, 행동 주체, 대상, 사거리, 자원과 권한을 검증한다.
2. 효과 계획과 안정적인 타격 순서를 만든다.
3. 비용 소비, 이동 또는 명중·피해·상태 효과, 후속 효과 큐를 처리한다.
4. 실제 피해 합산과 회복, 전투불능, 성장, 승패·시나리오 이벤트를 처리한다.
5. 상태 revision을 갱신하고 결과 이벤트를 반환한다.

거절된 명령은 상태·행동·재고·난수를 변경하지 않는다. 오류가 난 실행은 부분 변경을 외부에 노출하지 않도록 트랜잭션 또는 롤백을 구현한다. 시스템이 예기치 않게 실패하면 커밋 전 상태로 돌아가고 Session이 오류를 보고한다.

동일한 타격의 동일 특성은 중복 출처로 여러 번 적용하지 않는다. 후속 효과에는 원래 타격 가지 ID를 부여해 연쇄 종료 규칙을 적용한다. 의도된 광역 범위 중첩과 연쇄 방지의 중복 제한을 구분한다. 상세 피해·명중·회복 산식은 원문 1부와 2부를 따르고 미정 값은 버전이 있는 규칙 프로필에 둔다.

## 9. Go 공개 인터페이스

다음은 역할을 나타내는 API 초안이다. ECS world와 가변 컴포넌트 포인터를 어댑터에 반환하지 않는다.

```go
type Engine interface {
    Observe() Observation
    LegalActions(actor ActorID) ActionOptions
    Preview(command Command) (Preview, error)
    Apply(command Command) (CommandResult, error)
    Snapshot() (Snapshot, error)
}

type Policy interface {
    Choose(view Observation, options ActionOptions) (Command, error)
}
```

Observation은 revision, 진행 단계, 맵, 부대, 현재 차례, 시나리오 대기와 결과를 담는 읽기 전용 복사본이다. ActionOptions는 이동 칸·유효 대상·사용 병법·학습 목록을 압축해 제공하며 모든 조합을 무조건 열거하지 않는다. Preview는 예상 범위·비용·피해 범위를 반환하고 실제 게임 난수를 소비하지 않는다.

CommandResult는 성공 여부, 새 revision, 순서가 정해진 이벤트를 담는다. 실패 원인은 WrongPhase, NotYourTurn, InvalidTarget, OutOfRange, InsufficientMP, ActionSpent, IncompatibleEquipment 등 안정적인 코드와 사용자 설명으로 구분한다.

## 10. AI와 진행 제어

Session은 제어자와 AI 정책 버전을 실행 구성으로 관리한다. CLI에서 적 AI를 한 명령씩 진행해도 전투 규칙은 자동 모드와 같다. 외부 제어 모드에서는 자동 AI 실행을 끄고 적 명령도 지정된 제어자가 제출할 수 있으나 권한 검증은 유지한다.

초반 AI는 합법적인 이동·일반 공격·초기 병법·대기를 평가한다. 돌격은 접근과 피해, 원거리는 사거리와 생존, 책략은 적중·피해·회복을 평가한다. 동점은 안정적인 ID·좌표 순서로 해결한다. AI는 실제 판정 RNG를 예측하거나 소비하지 않는다. 확률적 탐색이 필요하면 별도 RNG를 사용하고 그 상태도 저장한다.

무작위 정책, 국사무쌍 같은 반복 행동, 명령 거절로 인한 무한 실행을 막기 위해 Session에 AI 명령 수·실행 시간 제한을 둔다. 제한 초과 시 중단하고 저장 가능한 경계에서 오류를 알린다. 불법 명령을 성공처럼 처리하거나 사용자의 차례를 자동으로 넘기지 않는다.

## 11. 저장과 불러오기

### 11.1 저장 가능한 경계

시나리오는 대사 표시 중·선택 대기·편성 준비에서 저장 가능하다. 전투는 아군과 적의 명령 처리 사이, 이동 확정 뒤 공격 전, 부대 대기 뒤, 턴 전환 완료 후 저장 가능하다. 적 AI 진행 중에도 다음 명령 경계에서 저장 요청을 처리한다.

코어 명령은 동기적으로 완결하며 명중·피해·후속 효과 처리의 중간 상태는 저장하지 않는다. 처리 중 접수한 저장은 완료 경계에서 수행하고 완료를 알려준다. 향후 애니메이션 재생 중에는 이미 확정된 코어 상태를 저장한다. 불러오기 후 해당 상태를 즉시 표시하며 지나간 피해 연출과 보상을 다시 실행하지 않는다.

이 경계에서는 처리 중 효과 큐가 비어 있어야 한다. Session은 저장할 스냅샷을 복사해 고정하며, 파일 쓰기 중 다음 명령이 실행되더라도 서로 다른 revision을 섞지 않는다.

### 11.2 저장 내용

| 구분 | 필수 내용 |
|---|---|
| 헤더 | save schema, core·content·rules·AI 버전, content hash, 생성 시간, 캠페인 ID |
| 캠페인 | 장수 성장·학습·장비, 창고·소모품, 출전 편성, 합류·보물·결과 이벤트 기록 |
| 시나리오 | 시나리오·노드 ID, 선택 대기, 지역 변수, 진행 커서 |
| 전투 | 스테이지·맵 변화, 부대 ID·위치·현재 자원·버프·행동 예산, 진영·라운드·차례 순서 |
| 재현 정보 | 초기 시드, 현재 RNG 상태, revision, 명령 로그 위치, 제어자·AI 정책 상태 |
| 결과 | 승패와 확정 보상, 다음 전이, 표시 대기 |
| 재도전 | 해당 전투의 출전 직전 체크포인트 |

저장은 버전이 있는 JSON DTO로 작성하고 ECS 메모리를 그대로 덤프하지 않는다. 전투 저장에서 roster만 복원해 전투를 다시 시작하는 방식은 금지한다. 이동 소모·독 지속시간·남은 MP·다음 AI 부대까지 그대로 복원한다. 시작 시드는 현재 난수 상태를 대체하지 못한다.

수동 슬롯에는 시나리오 또는 전투 이름, 라운드·진영 또는 대사 위치, 아군 요약, 저장 시간을 표시한다. 자동 저장은 시나리오 진입·전투 시작·결과 확정에서 수행하고 수동 슬롯을 덮어쓰지 않는다. 전투 도중 수동 저장은 라운드 시작에만 제한하지 않는다.

### 11.3 안전한 파일 처리

저장은 같은 디렉터리의 임시 파일에 기록·검증한 뒤 플랫폼이 지원하는 안전한 파일 교체를 사용한다. 필요하면 이전 파일 백업을 유지한다. 실패 시 기존 슬롯과 진행 중 상태를 보존하고 사용자에게 실패를 표시한다. 저장 완료는 파일 교체가 끝난 뒤에만 보고한다.

불러오기는 읽기 → 형식·버전·콘텐츠 검증 → 별도 엔진 복원 → 상태 불변조건 검증 → 현재 Session 교체 순서다. 손상·누락 ID·지원하지 않는 버전이면 현재 게임을 유지한다. 임의의 최신 데이터로 계속하거나 보물·장수를 조용히 제거하지 않는다. 첫 버전은 동일한 호환 버전만 지원하며 향후 migration은 명시적으로 추가한다.

브라우저 클라이언트에서는 파일 저장 대신 브라우저 저장소·파일 내보내기 어댑터를 구현하되 같은 저장 DTO를 사용한다. 체크섬은 손상 감지용이며 조작 방지 보장으로 설명하지 않는다.

## 12. CLI 사용 방식

### 12.1 사람용 모드

기본 실행은 시작 메뉴를 표시한다. 메뉴는 번호와 명령어를 함께 지원하고 help로 현재 단계에서 가능한 조작을 보여준다.

```text
srpg-cli
next                         현재 대사 진행
choose option_id             시나리오 선택
party                        장수·편성 조회
inventory                    창고·아이템 조회
equip liubei weapon item_id   시나리오 장비 장착
deploy liubei guanyu zhangfei 출전 준비
start-battle                 현재 준비의 전투 시작
map                          좌표·지형·부대 표시
unit unit_id                 부대 상세 조회
legal unit_id                가능한 행동·대상 조회
move unit_id x y             이동 확정
attack unit_id target_id     일반 공격
skill unit_id skill_id x y   병법 사용
item unit_id item_id target  아이템 사용
learn unit_id trait_id       전투 중 특성 습득
wait unit_id                 해당 부대 종료
end-faction                  남은 아군을 대기시키고 적 차례로
ai-step                      적 AI 한 명령 실행
save 1                       현재 상태를 슬롯 1에 저장
load 1                       슬롯 1 복원
menu                         진행 중 메뉴
quit                         저장 여부 선택 후 종료
```

좌표는 0부터 시작하며 x는 오른쪽, y는 아래쪽으로 증가한다. end-faction은 미행동 부대를 표시하고 사람용 모드에서 확인받는다. 조회·저장·메뉴는 이동·행동을 소비하지 않는다. 잘못된 명령에는 이유와 사용 예를 표시하고 진행을 유지한다.

### 12.2 JSON 모드

srpg-cli --json은 대화형 메뉴를 출력하지 않고 같은 시작 메뉴 상태를 구조화 응답으로 제공한다. stdin·stdout은 줄 단위 JSON, 진단은 stderr로 분리한다. 한 요청당 응답은 하나이며 그 요청과 적 자동 진행에서 생긴 이벤트는 해당 응답 안에 담는다. 자동 진행은 다음 사람 대기 또는 제한까지 수행하고, step 모드에서는 한 명령 경계까지만 수행한다.

```json
{"id":"r1","op":"menu.get"}
{"id":"r2","op":"game.new","seed":12345,"ai_mode":"step"}
{"id":"r3","op":"game.command","expected_revision":0,"command":{"type":"scenario.advance"}}
{"id":"r4","op":"save.write","slot":1,"overwrite":false}
{"id":"r5","op":"save.load","slot":1,"discard_current":true}
```

위 요청은 개별 형식 예시이며 연속 실행의 revision 값은 직전 응답에서 가져온다.

```json
{"id":"r4","ok":true,"revision":12,"result":{"slot":1,"saved":true},"events":[]}
```

게임 명령에는 expected_revision을 요구하고 오래된 상태에 대한 명령은 Conflict로 거절한다. 저장·불러오기·종료 확인은 명시 필드로 수행한다. 슬롯 존재 오류, 저장 손상, 잘못된 JSON을 구분하고 오류 후에도 프로세스가 요청을 받을 수 있다. quit 요청은 마지막 응답을 flush한 뒤 종료한다. EOF는 프로세스를 종료하지만 자동 진행 포기 저장을 임의로 만들거나 기존 슬롯을 덮어쓰지 않는다.

## 13. 재현성과 검증

동일한 core·content·rules·AI 버전, 초기 구성, 시드, 명령 순서에서 결과가 같아야 한다. ECS 쿼리와 Go map 순회를 게임 판정 순서로 사용하지 않는다. 판정 순서는 부대 ID·좌표·효과 우선순위로 정한다. 전투 내 판정은 순차 실행하고 서로 독립된 시뮬레이션만 병렬 실행한다.

능력치·피해 계산의 중간 소수점과 최종 내림 위치를 원문대로 유지한다. 숫자형·확률 비교·RNG 알고리즘을 고정하고 네이티브와 Wasm에서 동일한 사례를 검증한다. 저장 시간이 바뀌어도 게임 결과는 바뀌지 않아야 한다.

| 검증 | 기대 결과 |
|---|---|
| 첫 실행 | 네 가지 시작 메뉴, 저장이 없어도 정상 동작 |
| 도원결의 대사 저장 | 현재 대사와 세 장수 Lv1 상태로 재개 |
| 선택 대기 저장 | 같은 선택지가 표시되고 선택 효과 미적용 |

## 16. 최신 사용자 결정과 그래픽 버전 작업 기준 (2026-10-01)

이 절은 CLI 구현 후 밸런싱 대화에서 사용자가 정한 변경 사항이다. 이전 문서와 충돌하면 최신 사용자 지시를 우선한다. 현재 실행 코드는 아직 고정 비용 100, 격퇴 40, 승리 200의 기존 성장 규칙이며 아래 변경은 구현 대기 상태다.

### 16.1 확정 변경

- 성장 경험치는 일반 공격과 병법 공격으로 획득한다. 공격 병법의 경험치는 일반 공격의 2배다. 방어·피격 자체에는 경험치를 지급하지 않는다. 승리 경험치 지급을 없앤다.
- 상대 레벨이 높을수록 경험치를 더 얻는다. 격퇴를 일으킨 행동은 경험치에 추가 배율을 적용한다. 기본 행동 경험치·격퇴 배율과 레벨 차 보정 수치는 플레이 검증으로 조정할 초안이다.
- 작은 피해 반복, 회복된 적 재공격, 턴을 활용한 레벨 노가다는 의도한 육성 전략이다. 적별 경험치 상한, 반복 공격 감점, 회복 후 경험치 차단을 도입하지 않는다.
- 레벨별 필요 경험치 표를 사용하고 내부에는 실제 경험치를 저장한다. 화면의 유닛 정보에는 현재 레벨 필요량 대비 0~100으로 정규화해 표시한다. 경험치 초과분은 이월한다. 레벨업당 특성치 100은 유지한다.
- 통상적인 스테이지 진행에서 주력 출전 장수의 성장 목표는 약 +2레벨이다. 노가다·선택 교전으로 추가 성장은 허용한다. 모든 명령·경로에서 정확히 +2를 강제하지 않는다.
- 부관은 주장이 얻는 실제 경험치의 85%를 추가로 받는다. 주장의 획득량을 차감하지 않는다. 부관 자신의 레벨별 필요 경험치 표에 적용한다. 소수점 경험치 처리·누적 방식은 저장 가능한 결정적 규칙으로 정의한다.
- 부관 활용을 위해 중급 승급을 서두르고 독립 출전 부대를 줄이는 선택은 유효한 전략이다. 중급 Lv15·고급 Lv30 승급 조건, 전투 중 승급 아이템 사용, 승급 시 병력·병법치 완전 회복은 유지한다.
- 일기토는 스테이지 데이터에 정의된 아군·적 장수의 만남으로 발생하는 이벤트다. 승리·패배·무승부 및 양측의 퇴각·영구 사망을 정의할 수 있다. 일반 퇴각과 영구 사망을 구분해서 저장한다.
- 일기토 후 아군 참가자가 퇴각하거나 사망하지 않았다면 현재 레벨의 필요 경험치 한 회분을 지급해 1레벨 성장시킨다. 부관도 해당 실제 경험치의 85%를 받는다. 일기토 이벤트·경험치·결과는 고유 실행 키로 한 번만 적용하며 재로드로 중복 지급하지 않는다.

### 16.2 설계 초안과 장기 기준

- 필요 경험치 초기 후보: `round(100 × 1.035^(L−1))`. 지수 증가율은 확정값이 아니며 성장 분포를 확인해서 조정한다.
- 스테이지 번호 s를 1부터 세면 진입 기대 레벨은 `2s−1`, 일반 적 기준은 `2s`, 적 장수 기준은 `2s+2`다. 맵을 작성할 때 쓰는 기준이고 실제 적 레벨은 콘텐츠에 고정한다. 아군 현재 레벨을 읽어 자동 스케일링하지 않는다. 개별 보스·이벤트 적은 별도 프로필로 검증한다.
- 클리어 경로에서 보통 교전하는 적과 선택 교전을 나누어 경험치 예산을 계산한다. 이동 목표 승리 등에서는 전멸 경험치를 필수 성장량으로 가정하지 않는다.
- 25개 스테이지·총 아군 50명·최대 독립 출전 약 10부대를 장기 예시로 삼는다. 모든 장수가 Lv50에 도달할 필요는 없으며 주력 주장·부관 약 20명 육성을 기준으로 본다. 25개 스테이지 전체 콘텐츠 제작은 현재 초반 그래픽 버전의 범위로 자동 확장하지 않는다.
- 병종 비교는 동일 능력치·레벨·장비 예산의 가상 장수와 실제 장수 편성 양쪽에서 수행한다. 지형, 사거리, 이동, 병법치, 회복 기여를 포함한다.
- 동급 일반 부대의 격퇴까지 3~5 유효 타격, 튼튼한 부대는 5~7 타격은 초기 가설이다. 실제 피해/최대 HP, 집중 공격 급사율, 회복으로 교전이 정체되는 빈도와 함께 검증한다. 승률만으로 밸런싱 완료를 선언하지 않는다.
- 회복·버프·빗나감·반격·광역·지속 피해의 경험치와 일기토 세부 발동·결과 처리 등 판단이 모호한 부분은 영걸전 플레이 문화·공략을 우선 조사하고, 부족하면 조조전을 조사한다. 최신 사용자 확정 규칙은 참고 게임 관행보다 우선한다. 참고 자료와 선택한 초안의 이유를 기록한다.

### 16.3 작업 순서와 완료 증거

1. 경험치 비용표, 행동 경험치·레벨 보정·격퇴 배율, 정규화 표시를 코어와 CLI에 구현하고 저장 검증을 갱신한다. 기존 저장과 호환되지 않는 변경은 rules/content 버전으로 식별한다.
2. 승급·부관·일기토의 데이터, 명령, 상태, 이벤트, 저장·재도전·영구 사망 처리를 구현한다. 중급 승급과 부관의 실제 이용 가능한 시점은 성장·스테이지 공급에 맞춘다. 초반 세 전투만으로 Lv15 도달이나 승급 아이템 조기 공급을 강제하지 않는다. 기능 자체는 검증용 시나리오에서도 확인한다.
3. 병종별 타격/생존/병법치·지원 통계와 출전 장수별 성장 분포, 목표 경로별 경험치 예산을 출력하는 진단을 추가한다. 여러 시드·편성·전술을 비교하고 조정 근거를 남긴다.
4. 기존 Session/Core를 사용하는 Ebitengine 클라이언트를 연결한다. 시작·설정·저장·불러오기, 대사·선택지·편성·장비·부관, 맵·이동·행동·병법·아이템·학습·일기토·턴 진행·결과·재도전을 화면에서 조작할 수 있게 한다. 유닛 정보에 HP/MP와 정규화 경험치를 표시한다.
5. 새 게임부터 호로관 완료까지 그래픽 화면으로 실제 진행하고, 시나리오·이동 후·적 AI 명령 사이 저장·복원을 검증한다. CLI/GUI가 같은 코어 판정을 사용하는지 확인한다. `go test ./...`, `go vet ./...`, CLI·시뮬레이터·GUI 빌드, 화면 캡처와 실제 입력 검증을 완료한다.
